Recorded 2026-10-06 on the author's machine (Intel Core i7-13700H, 20 logical cores, Windows 11,
Python 3.14.5, sqlglot 30.21.0, PyArrow 25.0.1, DuckDB 1.5.6). CI re-runs the tests on Ubuntu with
Python 3.12.

## What the optimizer does to TPC-H Q3 (`make explain`, scale 1)

Without the optimizer the binder's literal plan is a filter over two cross products, estimated at
1.35 x 10^15 rows:

```
Limit 10
  Sort [revenue DESC, o_orderdate ASC, l_orderkey ASC]
    Project [...]
      Aggregate by [lineitem.l_orderkey, orders.o_orderdate] compute [sum(...)]
        Filter (customer.c_mktsegment = 'BUILDING' AND customer.c_custkey = orders.o_custkey AND ...)
          CrossJoin  (~1,351,505,250,000,000 rows)
            CrossJoin  (~2,250,000,000 rows)
              Scan customer [all 5 columns]  (~15,000 rows)
              Scan orders [all 6 columns]  (~150,000 rows)
            Scan lineitem [all 9 columns]  (~600,669 rows)
```

With it, every filter is in its scan, both join conditions came out of WHERE, the smallest filtered
relation (customer) is first, and each scan reads only what is used:

```
HashJoin ON (lineitem.l_orderkey = orders.o_orderkey)  (~13,348 rows)
  HashJoin ON (customer.c_custkey = orders.o_custkey)  (~10,000 rows)
    Scan customer [c_custkey] WHERE (customer.c_mktsegment = 'BUILDING')  (~3,000 rows)
    Scan orders [o_orderkey, o_custkey, o_orderdate] WHERE (orders.o_orderdate < DATE '1995-03-15')  (~50,000 rows)
  Scan lineitem [l_orderkey, l_extendedprice, l_discount] WHERE (lineitem.l_shipdate > DATE '1995-03-15')  (~200,223 rows)
```

The query then runs in under 80 ms and returns the same ten rows as DuckDB.

"Cells" is rows times columns read by the scans, before filters. Times are wall-clock milliseconds, best
of five, with both engines reading the same in-memory Arrow tables and returning an Arrow table.
Each query is timed before its literal plan runs, after a garbage collection; repeated runs on this
laptop still vary by about 20%.

### What the numbers say

- **Correctness first:** all 21 results equal DuckDB's at scale 1, as they do in the test suite at
  scale 0.01 with and without the optimizer.
- **The optimizer is what makes multi-table queries possible.** Q3 and Q10, written with comma
  joins, cannot run as written (the cross product is refused); optimized, they read 2.9 million
  cells and finish in under 80 ms. Over the 19 queries whose literal plan can run, the optimized
  plans read 35% of the cells.
- **One rule, measured:** `self_join` filters `a.l_orderkey <= 100` and joins on
  `a.l_orderkey = b.l_orderkey`. Without transitive predicates, `b` entered the join with all
  600,669 rows and the query took 52.9 ms (2.4x DuckDB). Copying the filter across the equality
  (ADR 0003, rule 2) shrinks `b` to about 400 rows before the join: 6.3 ms, against DuckDB's 23.7 ms.
- **Simple scans and filters are faster than DuckDB here, and that says little about engines.**
  `select_star` (2.2 ms vs 6.0 ms) or Q6 (9.3 ms vs 35.0 ms) mostly measure fixed per-query costs:
  DuckDB parses, plans and optimizes, sets up a scan of a foreign Arrow table and converts its
  result back to Arrow, while this engine already holds Arrow arrays and calls single Arrow
  kernels. The geometric mean of our time over DuckDB's, 0.53, is dominated by such queries.
- **Where we are slower, and why:**
  - Q1 (1.3x) and Q5 (1.2x): each expression is a separate kernel call that materializes a full
    intermediate column (`l_extendedprice * (1 - l_discount) * (1 + l_tax)` creates four
    600,000-value arrays), and the hash aggregate is single-threaded. DuckDB evaluates
    expressions over cache-sized vectors and aggregates in parallel. Pipelined execution over
    batches is M2.
  - `or_across_tables` (about even, 42.9 vs 43.7 ms, and slower in other runs): the `OR` uses
    columns of both tables, so it can only run after the join; this engine materializes the whole
    150,000-row join result and then filters it, where a pipelined engine streams join output
    through the filter in small vectors.
- **A cost we chose:** before a join that could exceed 50 million rows, the executor counts the
  keys on both sides to know the exact output size and refuses runaway joins. It filters the
  larger side to keys the smaller side has first, so the check costs little when the join is
  selective, and joins whose inputs multiply to less than the limit skip it entirely.
- **What this is not:** a TPC-H benchmark. The data is generated in memory with TPC-H's shapes,
  not dbgen's, and there is no Parquet I/O yet; the scale-factor-1 benchmark from Parquet with
  row-group skipping is M3.
